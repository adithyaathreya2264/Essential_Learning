# EssentialLearning

Study anything, offline. Upload your notes and get quizzes, flashcards, and explanations — no internet needed after setup, no accounts, no cloud, nothing leaves your phone.

## Privacy first, not privacy eventually

Privacy wasn't a feature bolted onto this app — it was the starting constraint the whole architecture was designed around. Concretely, not just as a claim:

- **There is exactly one network call in the entire app: the model download.** It happens once, on first launch (or when switching models in Settings), fetches a `.litertlm` file from Hugging Face, and verifies it against a published SHA256 checksum before it's ever loaded. After that download completes, the app has no further reason to make a network request, and doesn't.
- **No accounts, because there's nothing to attach an account to.** There's no login, no user ID, no server-side profile — your uploaded material and your study data live only in this app's local SQLite database, not because it's *not synced yet*, but because there is no sync path at all in the architecture.
- **Inference runs entirely on-device.** Every explanation, quiz, flashcard, and answer evaluation is generated by the model running locally on your phone's CPU/GPU. Your study material is never sent anywhere to be processed — it's the actual prompt input to a model executing on your own hardware.
- **No analytics, no crash reporting, no telemetry.** Nothing about how you use the app — which chapters you study, how you score, when you open it — is collected or transmitted. It only exists in your local database.
- **You can verify this yourself.** Put the phone in airplane mode after the model finishes downloading — every feature (chat, quiz, flashcards, reminders) keeps working. If you want to confirm at the network level, the app makes no outbound requests observable via a proxy/packet capture beyond the initial model fetch. This isn't a claim you have to take on faith.

This is also why some choices elsewhere in this README exist: no cloud fallback when a phone can't run a larger model (a smaller on-device model is used instead, never a remote one), no bundling of analytics SDKs, and no "sign in to sync across devices" feature — because that would mean introducing exactly the kind of server-side data path this project was built to avoid.

## Why this exists

Most "AI study app" projects either fake the offline part (silently calling a cloud API) or pick a model and hope it fits. This one doesn't do either. It runs a real LLM entirely on-device, picks the model based on what your phone can actually handle, and is explicit — in the UI, not just the code — whenever the AI's output doesn't match what you asked for.

## What it does

- **Upload** a PDF or TXT file and get it automatically split into editable chapters — rename, merge, split, reorder, or delete before anything is saved. Segmentation is rule-based, not AI-generated, so it works before the model has even finished downloading.
- **Ask** a chapter-scoped AI chat to explain, summarize, or answer questions in your own words. Context is isolated per chapter by design — the model never sees material outside what you're currently studying.
- **Quiz** yourself at a chosen difficulty. Generation and difficulty classification are two independent passes against the same rubric — if they disagree ("asked for hard, generated medium"), the app shows that mismatch honestly instead of silently retrying until it looks right. Answers are evaluated against the source content with explanations, not just scored.
- **Flashcards**, deliberately separate from quiz — quiz is for testing understanding, flashcards are for fast recall. Spaced repetition runs on a simplified FSRS scheduler (not the older SM-2 algorithm): rate each card Again/Hard/Good/Easy and it computes its own next review date. A Due Today view aggregates what's due across every chapter into one place.
- **Reminders** — a single daily notification aggregates due cards across all decks, instead of spamming one notification per card. You can also ask in chat to be reminded about a specific chapter.

## How the on-device AI actually works

This was the hardest part of the project, and the part I'd rather document honestly than gloss over.

- **Model choice adapts to the device.** The app offers **Gemma 4 E2B** (2.6 GB) and **E4B** (3.7 GB) for capable hardware, and falls back to **Qwen 3 0.6B** for lower-RAM devices where the Gemma models won't reliably load. This wasn't the original plan — it came out of hitting real out-of-memory failures on a mid-range test device and tracing the cause down to actual free RAM at load time, not context window size (which was my first, wrong assumption).
- **Rubric-driven difficulty calibration.** A shared prompt rubric combined with an independent classifier pass calibrates quiz difficulty — a deliberate choice over fine-tuning, which isn't worth doing until there's real usage data to validate against.
- **No bundled model.** The app itself stays small; the model is downloaded at runtime with resumable, checksum-verified transfer, since a dropped connection on a multi-gigabyte file is close to guaranteed at some point.
- **Constrained decoding, with a validation layer on top anyway.** Tool calls (explain/summarize/quiz/flashcards/evaluate/revise) use JSON-schema-constrained output, but responses are still schema-validated in-app with a capped retry — constrained decoding reduces malformed output, it doesn't eliminate the need to check.

## Install

1. Download the latest `.apk` from this repo's [Releases](https://github.com/adithyaathreya2264/Essential_Learning/releases/tag/Essential-Learning) page.
2. On your Android phone, enable "Install unknown apps" for your browser or file manager if prompted.
3. Open the downloaded APK to install.
4. On first launch, the app checks your device and recommends a model (Qwen 3 0.6B for lower-RAM phones, Gemma E2B for most phones, E4B for higher-end devices). Download happens over Wi-Fi in the background — this is the only setup step that needs a connection.

## Tech stack

- React Native + Expo (dev client), TypeScript, Expo Router
- On-device inference via `react-native-litert-lm` — Gemma 4 E2B/E4B or Qwen 3 0.6B depending on device capability, `.litertlm` format, constrained JSON-schema decoding
- `expo-sqlite` for local data, `expo-file-system` for resumable background model downloads
- `ts-fsrs` for spaced-repetition scheduling
- `expo-notifications` for local due-card reminders

## Known limitations — and which are deliberate

- **Voice input is intentionally not implemented.** It was scoped in the original plan but deliberately dropped to keep the text-based chat, quiz, and flashcard experience solid rather than splitting effort across a fourth input surface. Not a gap I didn't notice — a scope call.
- **DOCX upload is deferred, not abandoned.** No React Native–native DOCX text extraction library was mature enough to depend on at build time; PDF and TXT cover the primary use case. A DOCX path (likely a hand-rolled JSZip-based extractor, since DOCX is just XML in a zip) is a reasonable follow-up, not a redesign.
- **Android only**, distributed as a sideloaded APK via GitHub Releases — no Play Store submission.

## Development

```bash
npm install

```

Requires a dev client build (not Expo Go) since the app uses native modules — see `eas.json`'s `development` profile.

## Release process

This project ships as a versioned APK attached to a GitHub Release, built via EAS Build.

```bash
# one-time setup
npm install -D eas-cli
npx eas login
npx eas init                     # writes extra.eas.projectId into app.json

# build and release
npx eas build --platform android --profile production
npx eas-cli build:download --build-id <build-id>   # id printed in the build URL above

git tag vX.Y.Z && git push origin vX.Y.Z
gh release create vX.Y.Z ./<downloaded>.apk \
  --title "EssentialLearning vX.Y.Z" \
  --notes-file CHANGELOG.md
```
